# tällmi: stack research (October 2026)

What to build with, for a Mac app that is local-only, privacy-first and **light on resources**, on an M4 Pro with 24 GB that is also used for everyday work.

Three research passes went into this, on the app framework, local transcription, and the LLM/embeddings/storage stack. Numbers marked *(vendor)* or *(unverified)* still need checking on this Mac. Phase 0 exists to do that.

---

## TL;DR: recommended stack

| Layer | Pick | Resident cost | Runs on |
|---|---|---|---|
| App | **Native Swift + SwiftUI** (AppKit where needed), menu-bar app; **WKWebView + D3** only for the big visualizations | ~20–60 MB idle *(estimate)* | CPU |
| Final transcription | **Parakeet TDT 0.6B v3** via **FluidAudio** (Swift, Core ML) + Silero VAD | ~0.5 GB download, small peak RAM; ~200× real time *(vendor)* | **Neural Engine** |
| Live preview while talking | **Apple SpeechTranscriber** (macOS 26, built in) | 0 MB in the app | Neural Engine |
| Small LLM jobs (title, tags, one-line summary) | **Apple Foundation Models** (on-device model, typed output via `@Generable`) | 0 MB in the app (OS-managed) | Neural Engine/GPU |
| Cleanup and "ask my archive" | **Qwen3.5-4B, 4-bit, via MLX Swift**, loaded on demand and unloaded after ~60 s idle | ~3 GB only while loaded | GPU |
| Embeddings | **Qwen3-Embedding-0.6B** truncated to 512 dims, via MLXEmbedders | ~0.5–1 GB while loaded | GPU |
| Storage + search | **One SQLite file** (GRDB): FTS5 `unicode61` + FTS5 `trigram` (German compounds) + **sqlite-vec**, merged with RRF | ~50–200 MB on disk at 100k chunks | CPU |

**At idle the app is tens of MB.** Models load only while they work, and only one heavy model is loaded at a time. The worst case is about 4–5 GB, for a few seconds after a recording or while you ask a question.

## 1. App framework: Electron is no longer the default

| | Native SwiftUI | Tauri 2 | Electron |
|---|---|---|---|
| Idle RAM | ~20–60 MB *(estimate, no 2026 benchmark found)* | ~109 MB total (36 MB main + WebKit helpers) | ~128 MB, often 150–300 MB |
| Bundle | a few MB | < 1 MB minimal; tens of MB real | ~85–323 MB |
| Apple ML (Neural Engine, SpeechAnalyzer, Foundation Models) | **direct** | only via a hand-written Swift↔Rust bridge | only via native add-ons |
| "Provably offline" | **Sandbox without the network entitlement, so the OS blocks every connection** | possible, but a less-trodden path | hard: Chromium + npm surface |
| Custom visualizations | Swift Charts/Canvas, plus a WKWebView for D3/WebGL | best (web) | best (web) |
| iPhone companion later | shares most code (all of the above APIs exist on iOS 26) | Tauri mobile, but the same bridging problem | — |

Source for the Tauri/Electron numbers: [Better Stack, Jul 2026](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/).

**Why native wins here.** The things that make this app good are all Apple-native APIs that Swift calls directly: the Neural Engine via Core ML, SpeechAnalyzer, Foundation Models and MLX. With Tauri, every one of them would sit behind a Rust FFI layer that you'd maintain yourself, and Tauri's main advantage (cross-platform web UI) doesn't matter for a Mac-first app. Electron contradicts "light on resources" outright.

**Hybrid escape hatch.** The web stack is still used, but only where it shines: the "map of thoughts" (a 2D scatter of thousands of points with zoom and pan) is easier in D3/WebGL. It lives in a WKWebView that loads bundled local HTML only. Swift passes it JSON, and the web view's extra processes exist only while that window is open.

Considered and dropped: Electrobun (immature, 208 MB idle in tests), Deno Desktop, Flutter, React Native macOS, Kotlin Multiplatform, Wails, Dioxus, GPUI. None of them can reach Apple's speech/LLM APIs without bridges.

## 2. Local transcription: the field caught up with Whisper

German word error rate (WER) from the Open ASR Leaderboard paper, v4, March 2026 ([arXiv 2510.06961](https://arxiv.org/html/2510.06961v4)). Lower is better; FLEURS + CoVoST-2.

| Model | DE WER | Size | Mac runtime | Chip | Notes |
|---|---|---|---|---|---|
| Voxtral Small 24B | 3.01 | 24B | — | GPU | far too heavy |
| Cohere Transcribe 2B | 3.84 | 2B, ~2.6 GB | speech-swift (MLX) | GPU | **no timestamps** |
| Canary-1B-v2 | 4.10 | 1B | none on Mac | — | — |
| Qwen3-ASR 1.7B | 4.12 | ~2.4 GB | speech-swift (MLX) | GPU | timestamps via a separate aligner |
| **Parakeet TDT 0.6B v3** | **4.20** | **0.6B** | **FluidAudio (Swift, Core ML)** | **ANE** | ~210× real time on M4 Pro *(vendor)*; punctuation, timestamps, automatic language detection |
| Whisper large-v3 | 4.26 | 1.5B | WhisperKit | ANE | the old reference |
| Whisper large-v3-turbo | ~4.05 *(third party)* | 0.8B | WhisperKit | ANE | ~12× real time; mature SDK, word timestamps |
| primeline whisper-…-german | 3.0 CV-DE *(self-reported)* | 0.8–1.5B | WhisperKit after conversion | ANE | may weaken English |
| Apple SpeechTranscriber | **no German benchmark exists** | 0 (built in) | native | ANE | **one fixed locale per session**, so English phrases get forced into German spelling |

**Takeaways**

- The open models between 3.8 and 4.3 WER are all within about 0.4 points of each other on German, which is probably within benchmark noise. The deciding factor is **cost**, and there Parakeet v3 wins by a wide margin. It is a 0.6B model on the Neural Engine, so a 30-minute monologue takes about 10 s *(vendor)*.
- **Code-switching (German with English mixed in) is unbenchmarked for all of them.** Whisper picks one language per 30-second window and sometimes translates the English bits. Parakeet detects the language automatically, but how it handles a switch mid-sentence is undocumented. This is the single biggest unknown, and it can only be settled with your own recordings.
- Kyutai STT (English/French only), Moonshine, Granite Speech and VibeVoice turned up nothing useful for German.
- Long recordings: cut silence with VAD (Silero) and transcribe in chunks. FluidAudio does this.

**Live preview:** Apple SpeechTranscriber with volatile results adds nothing to the app size and is good enough for text that gets thrown away; the Parakeet result replaces it when you stop recording. The alternative is NVIDIA Nemotron 3.5 streaming multilingual 0.6B, which is newer and has an unclear license.

## 3. LLM: small is enough

| Model (4-bit) | RAM while loaded | Speed on M4 Pro | Role |
|---|---|---|---|
| Apple Foundation Models | 0 (OS) | fast | titles, tags, short summaries. **~4K-token context on macOS 26**, too small for RAG over many entries |
| **Qwen3.5-4B** | ~3 GB *(unverified)* | — | **default** for cleanup + RAG answers (Apache-2.0, 201 languages, run with thinking off) |
| Gemma 4 E4B | ~5.5–6 GB | ~57 tok/s | alternative |
| Qwen3.5-9B | ~7 GB peak | ~46–50 tok/s generation | "better answers" option |
| Qwen3.6-35B-A3B / Gemma 4 26B-A4B | 16–22 GB | ~2 tok/s on 24 GB due to swapping | **avoid** on this Mac |

Prior art: Hyprnote/Char handles note structuring with a fine-tuned 1.7B Qwen, which suggests small models are enough for structured note tasks.

**Runtime: MLX Swift (`mlx-swift-lm`)**, running inside the app process with no daemon. Load and unload are under our control. It is faster than llama.cpp on Apple Silicon. Ollama now has an MLX backend too, but it is a separate background server, which is the wrong shape for a private standalone app. It stays useful as an optional "bring your own local server" setting for experiments.

*To verify:* that `mlx-swift-lm` supports Qwen3.5 / Gemma 4 out of the box.

| bge-m3 | 0.6B | 59.6 | MIT |

| Qwen3-Embedding-4B | 4B | 69.5 | Apache-2.0 (heavier option) |

**Qwen3-Embedding-0.6B at 512 dims** gives the best quality per MB with a clean license. EmbeddingGemma-300M is the lightest fallback. **Qwen3-Reranker-0.6B** (optional) re-sorts the top ~30 hits for "ask" questions.

We still need German-only scores, so Phase 0 builds a small German evaluation set from real entries.

## 5. Storage and search

- **SQLite (GRDB.swift)**: one file, with transactions; GRDB supports FTS5 tokenizers.
- **German full text:** FTS5 has no German stemmer.
  - Use `unicode61` (umlauts and ß kept) for whole words.
  - Add a second **`trigram`** FTS5 table, so "Angst" also finds "Zukunftsangst".
- **sqlite-vec** v0.1.9 (March 2026) is still pre-1.0 but active, with DELETE support and DiskANN in alpha.
  - At 100k chunks × 512 dims: ~200 MB as float32, ~50 MB as int8.
  - Brute-force search there should take tens of ms *(unverified)*.
  - If it ever gets slow: USearch (HNSW). LanceDB, Chroma and DuckDB are overkill at this scale.
- **Hybrid ranking:** Reciprocal Rank Fusion (k=60) of the keyword and vector results.
- Prior art: [RewindOS](https://deepwiki.com/jaypopat/rewindos/3.2-search-architecture) uses exactly FTS5 + sqlite-vec hybrid search. Screenpipe is FTS5-only and gets criticized for literal-match-only search, which argues for the semantic layer.
- New at WWDC26: a Spotlight-backed local RAG search tool for Foundation Models. It's worth a look later, but its German quality is unknown.

## 6. Resource budget

| State | What is loaded | RAM |
|---|---|---|
| Idle (menu bar) | app + SQLite | **tens of MB** |
| Recording | + SpeechTranscriber (OS) + audio buffer | + ~0 (OS-managed) |
| After recording, ~10–30 s | Parakeet → Foundation Models → embedder, **one after another** | peak ~1 GB |
| Cleanup pass (optional, background) | Qwen3.5-4B | ~3 GB, unloaded after |
| Asking a question | embedder + reranker + Qwen3.5-4B | ~4–5 GB for the duration |
| Map view open | + WKWebView helpers | + ~100 MB |

Rules: never keep two heavy models loaded at once, unload after idle, run background work at low QoS, and skip heavy jobs on battery or under memory pressure.
